Acceptance checks

    Prove a recovery

    1. On a blank estate, provision two hosts with at least 6 GiB of memory and more than 16 GB of storage each. Deploy the database and application on both. Issue server certificates. Point application DNS at your primary host.
    2. Grant database access to svc-app, admin to engineer and view to operator. Write a production record as engineer. Test reads as operator and visitor. Compare the audit entries.
    3. Replicate to the standby and back up the primary to the independent archive. Advance the clock 10 s and write a second record. Predict which committed transactions the standby can recover.
    4. Power down the primary, advance 20 s and switch application DNS to the standby. Inspect recovery time, the recovered transaction IDs and the missing count. Repeat with a freshly synchronised replica.
    5. Patch the standby application to v2 and run its canary probe. Compare schema migration with rollback. Corrupt a backup and try a restore. Record which checks protect data and which protect availability.
    I don't know yet

    Domain Name System (DNS) resolves the service name to one host. Start with the reference estate. Write one record, replicate, then take the primary offline. Advance 12 s before changing DNS. A healthy standby should show one record and a 12 s outage.

    Recovery time objective (RTO) limits the interval from first failed service health to a passing end-to-end service probe. Recovery point objective (RPO) limits how far back committed data had to be recovered. The model also reports the actual missing transaction IDs. The monotonic clock advances only when you choose an elapsed interval. Memory is in binary GiB; storage uses decimal GB. Each synthetic record reserves 0.01 GB. Recovery, identity and host administration run entirely inside this project.

    Shared infrastructure incident

    A virtual machine (VM) depends on its hypervisor and its own data volume. Commission a Linux primary and Windows standby, then assign both to one hypervisor. Write a record, replicate it and predict whether changing DNS will restore service after that hypervisor fails. Restore it, place the standby in a different failure domain, and repeat. Compare the application probe, missing IDs and the outage interval.

    Add a second equal-size data disk to form a RAID 1 mirror. The mirror has one disk's usable capacity and two copies of the records. Fail one member: the volume should still serve records. Replace it and inspect the audit. Test both members lost on a saved variant, recover onto an empty replacement and retrieve the restored transaction. Software and service configuration are kept separately from the simulated data volume. Mirror rebuild is instantaneous in this exercise.

    For the patch drill, upgrade the standby before moving DNS. Probe the incompatible version, change schema or roll back and verify a passing canary. For the archive drill, corrupt the backup and verify a restore is blocked. Keep its integrity evidence before taking a new backup.
